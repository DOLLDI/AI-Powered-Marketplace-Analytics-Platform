# Архитектура

## Общая схема

```text
Telegram / VK
    |
FastAPI routers
    |
platform handlers
    |
services: WB parser, SmartCheck, billing, DB, prompts, antiflood
    |
PostgreSQL / SQLite, ProxyAPI/OpenAI, Wildberries API, payment providers
```

Приложение запускается как FastAPI-сервис. Внутри lifecycle поднимаются фоновые задачи: обработка платежных side-effects, повторная отправка чеков, обслуживание старой истории и, при необходимости, Telegram polling.

## Входные точки

```text
/telegram/webhook           Telegram webhook
/vk/webhook                 VK Callback API
/billing/*                  checkout, return, provider webhooks
/admin/login                вход в админку
/admin/panel                HTML-админка
/health                     healthcheck
/ready                      readiness check
```

## Основные модули

```text
app/main.py
```

Создает FastAPI app, валидирует runtime-конфиг, настраивает webhook, запускает фоновые workers.

```text
app/services/config.py
```

Единая модель настроек. Читает `.env.local`, `.env`, `.env.prompts`.

```text
app/services/db.py
```

Абстракция над SQLite/PostgreSQL. Хранит пользователей, историю, платежи, рефералов, чеки и состояние VK duplicate protection.

```text
app/services/wb.py
```

Парсинг Wildberries и SmartCheck-аналитика.

```text
app/services/billing.py
```

Создание платежей, проверка статусов, начисление тарифов, retry side-effects.

```text
app/routers/admin.py
```

HTML-админка, статистика, пользователи, платежи, рассылка, ручные операции.

## SmartCheck pipeline

1. Из сообщения извлекается ссылка WB или артикул.
2. Загружается карточка товара.
3. Для отзывов сначала используется `root_id`, затем fallback по артикулу.
4. Отзывы грузятся пачками с учетом:
   - `WB_MAX_REVIEWS_TOTAL`;
   - `WB_BATCH_SIZE`;
   - `WB_MAX_PARSE_SECONDS`;
   - `WB_REQUEST_DELAY_SECONDS`;
   - `WB_PROXY_URL`;
   - `WB_ENABLE_ROTATING_PROXIES`.
5. Результат кэшируется по товару и настройкам.
6. Локальный анализ считает статистику, риски и сигналы накрутки.
7. Категория товара сопоставляется с риск-профилем.
8. Код выбирает recommended verdict.
9. AI получает summary-pack и пишет короткое объяснение.
10. Ответ нормализуется перед отправкой пользователю.

## Риск-профили

Система не оценивает все товары одинаково. Например, у одежды чаще встречаются размерные нюансы, а у электроники серьезнее воспринимаются поломки и неисправности.

Профили:

- `apparel` - одежда, белье, размеры, посадка, ткань.
- `electronics` - электроника, работоспособность, брак, гарантийные риски.
- `beauty_health` - косметика, БАДы, запах, упаковка, субъективный эффект.
- `default` - общий профиль.

## Проверка накрутки отзывов

SmartCheck выделяет отдельный блок `Проверка накрутки отзывов`. Логика сделана осторожной:

- короткие отзывы сами по себе не считаются накруткой;
- микроповторы считаются слабым сигналом;
- подозрительность появляется только при совокупности сигналов;
- сильные выводы допускаются только при серьезных аномалиях из summary-pack.

Уровни:

- `низкий риск`;
- `слабые вопросы`;
- `подозрительно`;
- `высокий риск`.

## Вердикт

Финальный verdict выбирается кодом, а не свободной фантазией AI. AI объясняет уже рассчитанное решение.

Возможные значения:

- `РЕКОМЕНДУЕМ` - сильная карточка, высокий рейтинг, низкая доля серьезных проблем.
- `РИСКОВАННО` - есть заметные риски, которые могут повлиять на покупку.
- `НЕ РЕКОМЕНДУЕМ` - много сильных негативных сигналов или критичные проблемы.

## Лимиты и доступ

Пользователь имеет профиль:

- тариф;
- баланс проверок;
- дневной бесплатный лимит;
- PRO-срок;
- referral code;
- blocked flag.

Перед обработкой запроса проверяются antiflood и доступ к проверкам. После успешного анализа лимит списывается.

## Billing

Поддерживаются:

- `sandbox`;
- `yookassa`;
- `robokassa`.

Платежный flow:

1. Пользователь выбирает тариф.
2. Создается payment token.
3. Провайдер возвращает пользователя на return URL или отправляет webhook/result.
4. Платеж помечается как оплаченный.
5. Side-effect worker начисляет тариф и реферальный бонус.
6. При включенной фискализации создается чек.

Side-effects идемпотентны: повторный webhook не должен начислить тариф дважды.

## Admin

Админка использует cookie-сессию на базе `ADMIN_TOKEN` и `ADMIN_IDS`.

Функции:

- статистика;
- список пользователей;
- поиск пользователя;
- блокировка;
- выдача проверок;
- выдача PRO;
- просмотр платежей;
- ручное подтверждение платежа;
- повторная отправка чека;
- rich-рассылка;
- хвост error-log.

## Broadcast

Рассылка работает по пользователям в базе:

- Telegram: отправка текста, изображения и inline-кнопки.
- VK: отправка текста, загрузка изображения в сообщения и кнопка.

Недоступные пользователи могут быть помечены заблокированными, чтобы не портить следующие рассылки.

## VK Delivery

VK использует два канала доставки входящих сообщений:

- Callback API: основной webhook `/vk/webhook`.
- Long Poll fallback: фоновый worker получает `message_new` напрямую из VK API.

Оба канала ведут в один обработчик. Дедупликация идет по `peer_id:conversation_message_id`, поэтому одно сообщение не должно обрабатываться дважды, даже если VK доставит его через оба канала.

## Хранилище

Production:

```env
DB_BACKEND=postgres
DATABASE_URL=postgresql://proxyapi:proxyapi@postgres:5432/proxyapi
```

Локально:

```env
DB_BACKEND=sqlite
SQLITE_DB_PATH=users.db
```

Для production рекомендуется только PostgreSQL.

## Наблюдаемость

- Docker healthcheck дергает `/ready`.
- Ошибки пишутся в `ERROR_LOG_PATH`.
- Глобальный middleware логирует непойманные исключения.
- В админке доступен хвост error-log.
